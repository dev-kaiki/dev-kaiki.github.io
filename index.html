One machine, three problems

A CNC machine needs programs sent to it, needs a way to send them that isn’t a laptop on a cart, and needs fixing when it throws an alarm at 2 AM. I built all three sides in production at SMI.

Selected work

All three run in production at SMI and are published with the company's permission.

dnc-serial-engine

C++17QtCMakeRS-232

An RS-232 DNC engine that streams G-code to CNC controllers — fast enough to be useful, slow enough never to drop a block mid-cut.

A controller from the 1980s has a few kilobytes of buffer and no way to report how full it is. You get one bit of backpressure, and it arrives late. Send too fast and the machine silently drops characters while cutting steel; send too slow and drip-feeding a program larger than the machine's memory stops being viable. The engine treats flow control as a control loop: chunk size grows while the machine drains and downshifts the moment XOFF arrives early.

The engineering log documents the real debugging history on live machines — including the overflow fix that created a throughput ceiling, and the ceiling fix that brought back mid-program choking.

dnc-android

Qt 6QMLC++17JNIUSB serial

The same engine on a tablet bolted to the machine — reaching RS-232 through USB OTG, an FTDI chip and a JNI bridge, because Android has no serial port.

The transmission engine was ported unchanged behind an extracted ISerialPort interface: throwing it away would have discarded every bench session that tuned it. Getting it to send took finding five faults that produced no visible error — a zero read-timeout parking the USB reader thread so writes were silently swallowed, a signal poller running 1000 control transfers per second against the writer with no lock, and a flow-control request the FTDI library rejected on a name mismatch while continuing as if it had worked.

The last one was confirmed by reading the library's bytecode: controlTransfer(0x40, 2, 0x1311, port|0x0400) is SIO_SET_FLOW_CTRL with SIO_XON_XOFF_HS — byte for byte what the Windows driver writes.

maia-cnc-assistant

PythonFastAPIRAGpgvectorFlutter

A RAG assistant over a company's technical archive, reaching technicians through a Flutter app and WhatsApp.

When a controller throws an alarm at 2 AM the answer usually exists — in a 400-page PDF nobody can search, or in the head of the one technician who is asleep. Industrial maintenance breaks generic RAG in specific ways, and most of the codebase is the response: a multi-stage answer pipeline with an explicit safety policy (a hallucinated procedure on a live machine injures someone), Drive ingestion gated behind a human review queue, and cost guards at request, daily and monthly level so a retry loop cannot burn the budget overnight.

Provider migration is done with shadow wrappers that run the new path alongside the live one and log the differences — verified against real traffic before being switched on.
